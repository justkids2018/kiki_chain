# Kiki 管理后台 UI 体系升级

## 功能名称

借鉴 Agentia 管理后台视觉语言，升级 Kiki 管理后台公共框架与用户管理示范页。

## 背景与动机

- **解决什么问题**：统一 `kiki_admin` 的后台视觉体系，提升信息密度、层级辨识度与日常操作效率。
- **当前痛点**：现有页面缺少统一、可复用的后台壳层与视觉规范，不利于后续功能扩展和一致性维护。
- **不做会怎样**：新增页面会继续形成局部样式和交互差异，整体体验与维护成本逐步恶化。

## 用户故事

- US-1：作为后台管理员，我希望导航、筛选、表格和操作区拥有清晰一致的层级，以便快速定位和处理数据。
- US-2：作为开发维护者，我希望视觉基础能力由 Kiki 自有组件和设计变量承载，以便各业务模块独立演进。
- US-3：作为产品负责人，我希望先通过用户管理页验证改造效果，再安全推广到其他后台页面。

## 验收标准（Acceptance Criteria）

- AC-1：Given 管理员进入任一后台业务页，When 页面完成加载，Then 顶部栏、侧边栏和内容容器使用统一的 Kiki 后台视觉体系，现有导航仍可正常工作。
- AC-2：Given 管理员进入用户管理页，When 查看和筛选用户，Then 可清晰看到页面标题与说明、筛选区、数据表格、分页与行操作，功能与现有接口保持一致。
- AC-3：Given 用户管理表格出现较长文本或不同状态，When 页面展示数据，Then 文本截断、状态标签和操作按钮有稳定布局，不造成主要列错位。
- AC-4：Given 常见桌面窗口宽度，When 侧栏展开或收起，Then 主内容区正确适配，不出现遮挡或不可操作区域。
- AC-5：Given 开发者检查实现，When 追踪样式和组件依赖，Then 公共视觉变量与壳层属于 `kiki_admin` 自有实现，业务页面不依赖参考站代码或运行资源。
- AC-6：Given 改造完成，When 执行类型检查与生产构建并进行页面截图验收，Then 构建通过，用户管理核心交互无回归，页面视觉层级与参考方向一致但具有 Kiki 品牌辨识度。

## 边界 / 不在范围内（Out of Scope）

- ❌ 不逐像素复刻 Agentia，也不复制其代码、资源、Logo、文案或专属业务结构。
- ❌ 本阶段不一次性重写场景、分类、反馈等全部业务页面。
- ❌ 不改变后端接口、数据库结构、认证授权模型或用户数据语义。
- ❌ 不新增参考站特有的角色分配、删除等 Kiki 当前未定义业务能力。
- ❌ 不以大规模替换 UI 框架为目标，优先基于现有 Vue 3 与 Element Plus 演进。

## 数据需求

- 新增字段 / 表：无。
- 修改字段 / 表：无。
- 数据迁移需要：否。

## 非功能需求

- **性能**：不增加额外远程视觉资源依赖；首屏与表格交互性能不低于现状。
- **安全**：沿用现有认证和权限控制，不在前端暴露额外敏感信息。
- **兼容性**：保持当前项目支持的现代桌面浏览器；优先适配 1280px 及以上后台工作区，并保证窄窗口可用。
- **可维护性**：设计变量、公共布局和业务页面职责分离；页面改造可逐模块迁移、验证和回滚。
- **可观测**：本次无新增运行监控；构建结果和 UI 截图作为验收证据保存。

## 风险与未知

- 风险 1：公共布局变化可能影响全部页面；采用渐进式样式兼容和逐页回归降低风险。
- 风险 2：表格信息密度提高后，窄屏可能出现拥挤；通过列宽、截断、横向滚动和响应式策略处理。
- 未知 1：现有用户管理接口字段与参考图列定义并不相同；以现有业务字段为准，在现状分析阶段确认可展示内容。
- 未知 2：Kiki 当前品牌色和 Logo 资产的完整规范需在现状分析阶段确认，不使用参考站品牌资产替代。
