> **适用范围**: 所有多端架构项目
> **版本**: v1.0

## 📋 核心原则

### 1. 理解优先原则（Understand First）

**定义**: 在分解任务前，必须完全理解需求

**实践**:
- ✅ 复述用户需求，确认理解
- ✅ 识别模糊点，主动提问
- ✅ 明确功能边界和验收标准
- ❌ 不要基于假设进行任务分解

**示例**:
```
用户: "优化场景功能"

❌ 错误做法:
直接分解任务 → 可能理解错误

✅ 正确做法:
提问: "您指的是哪方面的优化？
- 性能优化（加载速度）？
- UI/UX 优化（界面体验）？
- 功能增强（新特性）？
具体是移动端还是管理后台？"
```

---

### 2. 依赖识别原则（Dependency Awareness）

**定义**: 正确识别任务之间的依赖关系

**常见依赖模式**:

1. **数据依赖**
   ```
   数据库设计 → 后端实现 → 前端实现
   ```

2. **接口依赖**
   ```
   API 定义 → 后端实现 → 前端集成
   ```

3. **功能依赖**
   ```
   用户认证 → 权限控制 → 业务功能
   ```

**依赖分析清单**:
- [ ] 是否需要新的数据表？
- [ ] 是否依赖其他 API？
- [ ] 是否需要第三方服务？
- [ ] 前端是否依赖后端完成？

---

### 3. 优先级判断原则（Priority Assessment）

**优先级定义**:

| 级别 | 定义 | 示例 |
|------|------|------|
| P0 | 阻塞性，必须立即完成 | 生产环境崩溃、安全漏洞 |
| P1 | 高优先级，核心功能 | 用户登录、核心业务流程 |
| P2 | 中优先级，重要但不紧急 | 功能优化、性能提升 |
| P3 | 低优先级，锦上添花 | UI 美化、辅助功能 |

**判断标准**:
1. **影响范围**: 影响多少用户？
2. **业务价值**: 对业务的重要性？
3. **技术风险**: 实现难度和风险？
4. **依赖关系**: 是否阻塞其他任务？

---

### 4. 任务分解原则（Task Decomposition）

**SMART 原则**:
- **S**pecific: 具体明确
- **M**easurable: 可衡量
- **A**chievable: 可实现
- **R**elevant: 相关性强
- **T**ime-bound: 有时间限制

**分解粒度**:
- ✅ 单个任务 1-4 小时完成
- ✅ 任务可独立验收
- ✅ 任务有明确的输入输出
- ❌ 避免过大的任务（>1天）
- ❌ 避免过小的任务（<30分钟）

**示例**:
```
❌ 错误分解:
"实现用户系统" （太大，无法估算）

✅ 正确分解:
1. 实现用户注册 API (2h)
2. 实现用户登录 API (1.5h)
3. 实现 JWT 认证中间件 (2h)
4. 实现用户信息更新 API (1h)
5. 移动端登录界面 (2h)
6. 移动端注册界面 (2h)
```

---

### 5. 协调执行原则（Coordination）

**串行 vs 并行**:

**串行执行**（有依赖）:
```
Task A → Task B → Task C
```
- 适用场景: B 依赖 A 的输出，C 依赖 B 的输出
- 示例: 数据库设计 → 后端实现 → 前端集成

**并行执行**（无依赖）:
```
Task A ║ Task B ║ Task C
```
- 适用场景: 任务之间无依赖关系
- 示例: 移动端 UI || 管理后台 UI || 文档编写

**混合执行**:
```
Phase 1: Task A (串行)
         ↓
Phase 2: Task B ║ Task C (并行)
         ↓
Phase 3: Task D (串行)
```

## 🚫 反模式（Anti-Patterns）

### 反模式 1: 过早优化

❌ **错误做法**:
```
用户: "实现用户登录"
→ 立即考虑: 分布式 session、Redis 集群、负载均衡...
```

✅ **正确做法**:
```
用户: "实现用户登录"
→ 先实现基本功能: JWT 认证
→ 后续根据需要优化
```

---

### 反模式 2: 忽略依赖

❌ **错误做法**:
```
同时开始:
- 前端实现（调用 API）
- 后端实现（提供 API）
→ 结果: 前端等待后端，浪费时间
```

✅ **正确做法**:
```
Phase 1: 后端实现（优先）
Phase 2: 前端实现（等待后端完成）
```

---

### 反模式 3: 任务过大

❌ **错误做法**:
```
任务: "实现整个用户系统" (预计 3 天)
→ 无法跟踪进度，风险高
```

✅ **正确做法**:
```
任务 1: 用户注册 API (2h)
任务 2: 用户登录 API (1.5h)
任务 3: 用户信息 API (1h)
...
→ 每个任务可独立验收
```

---

### 反模式 4: 缺少验收标准

❌ **错误做法**:
```
任务: "优化性能"
→ 无法判断是否完成
```

✅ **正确做法**:
```
任务: "优化场景列表加载性能"
验收标准:
- 首屏加载时间 < 1s
- 滚动流畅度 60fps
- 内存占用 < 100MB
```
