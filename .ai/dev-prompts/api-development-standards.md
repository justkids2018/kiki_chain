# API 开发规范

## 1. API 文档强制要求

**核心原则：前后端接口以 API 文档为唯一标准，保证接口一致性**

### 1.1 文档位置
- 统一放在 `docs/api/` 目录（项目根目录）
- 按功能模块组织：`docs/api/endpoints/{module}.md`
- 参考：`docs/api/README.md` 了解完整规范

### 1.2 强制更新规则
**每次开发新功能时，必须同步更新 API 文档，包括：**
- 新增接口：添加完整接口文档
- 修改接口：更新参数、响应结构或说明
- 删除接口：标记为已废弃并说明替代方案

### 1.3 接口文档必填内容
每个接口必须包含：
- 接口描述、请求方式、接口路径
- 请求参数（包括类型、必填、说明、示例）
- 响应参数（包括数据结构说明）
- 请求和响应示例（完整 JSON）
- 错误码说明和处理建议

### 1.4 前后端协作流程
1. **接口设计阶段**：后端先编写 API 文档
2. **评审确认**：前后端评审接口文档
3. **并行开发**：前端根据文档 mock，后端根据文档实现
4. **联调验证**：以文档为标准验证接口一致性
5. **文档同步**：任何变更必须立即更新文档

### 1.5 Code Review 检查点
- PR 中如果涉及接口变更，必须包含对应的 API 文档更新
- 文档与代码不一致时，PR 不予通过

## 2. 响应格式统一规范

所有 API 接口响应必须遵循统一格式：

```json
{
  "code": 200,           // 状态码：200 成功，其他为错误码
  "message": "success",  // 响应消息
  "data": {}             // 业务数据（可为对象或数组）
}
```

### 错误码规范

| 错误码 | 说明 | 处理建议 |
|--------|------|----------|
| 200 | 成功 | 正常处理 |
| 400 | 参数错误 | 检查请求参数格式和类型 |
| 401 | 未授权 | token 过期或无效，需要重新登录 |
| 403 | 无权限 | 该用户无权访问该资源 |
| 404 | 资源不存在 | 检查请求路径和资源 ID |
| 500 | 服务器错误 | 稍后重试或联系技术支持 |

## 3. 开发流程最佳实践

### 文档驱动开发（Documentation-Driven Development）

```
接口设计 → API 文档 → 评审确认 → 并行开发 → 联调验证
```

**优势**：
- 前后端开发可以并行进行
- 接口契约清晰，减少沟通成本
- 文档即契约，降低联调风险

### 开发检查清单

开发新功能时，确保完成以下步骤：

- [ ] API 文档已编写（`docs/api/endpoints/{module}.md`）
- [ ] 前后端已评审并确认接口
- [ ] 后端实现符合文档定义
- [ ] 前端调用符合文档定义
- [ ] 响应格式符合统一规范
- [ ] 错误处理已覆盖所有错误码
- [ ] 测试覆盖正常流程和异常流程
- [ ] PR 包含 API 文档更新（如有变更）

## 4. 常见问题

### Q: 什么时候需要更新 API 文档？

A: 以下情况必须更新文档：
- 新增接口
- 修改接口路径、请求方法
- 修改请求参数或响应参数
- 修改响应数据结构
- 接口废弃或删除

### Q: 如何保证文档和代码一致？

A: 
1. 在开发前先写文档（文档驱动开发）
2. PR 时必须检查文档更新
3. 定期进行文档和代码的一致性检查
4. 使用工具自动生成部分文档（如 Swagger）

### Q: 前后端接口不一致怎么办？

A: 以 `docs/api/` 中的文档为唯一标准：
1. 确认文档是否是最新版本
2. 如果文档正确，修改代码以符合文档
3. 如果文档错误，先更新文档再修改代码
4. 文档变更必须通知前后端双方

## 5. AI Agent 提示

当你（AI Agent）开发涉及接口的功能时：

1. **先查阅 API 文档**：`docs/api/endpoints/{module}.md`
2. **如果接口不存在**：先创建 API 文档，再实现代码
3. **如果需要修改接口**：先更新 API 文档，再修改代码
4. **提交 PR 时**：确保 API 文档已同步更新

**记住：API 文档是唯一真理来源，代码必须遵循文档！**
