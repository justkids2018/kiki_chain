# 通用开发规范（Common Development Guidelines）

> **适用范围**: 所有编程语言和项目
> **版本**: v1.0
> **最后更新**: 2026-01-19

---

## 🛑 核心工作流

### 1. 上下文确认阶段
**目标**: 确保理解需求，避免无效开发

- ✅ 复述用户需求与目标，确认理解
- ✅ 若存疑，最多提 3 个精准问题
- ❌ **此阶段禁止交付成品代码或文档**

**示例**:
```
理解确认：
1. 需求：为用户管理模块添加批量删除功能
2. 目标：支持一次删除多个用户，需要权限验证
3. 疑问：
   - 删除后是否需要软删除（保留数据）还是硬删除？
   - 批量操作的最大数量限制是多少？
   - 是否需要操作日志记录？
```

---

### 2. 讨论与设计阶段
**目标**: 迭代方案，验证可行性

- ✅ 确认理解后，开始方案设计
- ✅ 可发送"草案代码"或"伪代码"验证思路
- ✅ 优先考虑：准确性 > 可落地性 > 可维护性
- ✅ 发现风险或边界问题时，主动提问

**示例**:
```
方案草案：
1. API 设计：POST /api/v1/users/batch-delete
2. 请求参数：{ user_ids: [1, 2, 3] }
3. 权限检查：需要 ADMIN 角色
4. 删除策略：软删除（设置 deleted_at 字段）
5. 风险：
   - 批量删除可能影响性能，建议限制最大 100 个
   - 需要事务保证原子性
```

---

### 3. 成品交付阶段
**目标**: 一次性交付完整、可用的代码和文档

- ⚠️ **仅在收到"生成文档/交付代码"指令后执行**
- ✅ 按照下面的"交付清单"一次性提交完整结果
- ✅ 包含代码、文档、测试建议、自检清单

---

## 📑 交付清单（Delivery Checklist）

### 交付顺序（贴合开发流程）

#### 1. 任务概览
- 关键目标（1-2 句话）
- 背景说明
- 受影响范围（模块、文件、API）

**示例**:
```
任务：为用户管理模块添加批量删除功能
目标：支持管理员一次删除多个用户（软删除），最大 100 个
影响：user_service.rs、user_repository.rs、/api/v1/users 路由
```

---

#### 2. 上下文与假设
- 需求要点
- 依赖关系（数据库、第三方服务）
- 边界条件（限制、约束）
- 待确认事项（标记为 "待确认"）

**示例**:
```
依赖：
- PostgreSQL 事务支持
- 权限系统（AdminGuard）

边界：
- 最大批量删除数量：100
- 删除策略：软删除（保留数据）
- 权限：仅 ADMIN 角色

待确认：
- 是否需要删除关联数据（如用户的订单）？
```

---

#### 3. 架构蓝图（核心重点）⭐
- 系统/模块关系图
- 组件职责说明
- 数据流向（请求 → 响应）

**示例**:
```
调用链：
API Handler → Use Case → Repository → Database
    ↓            ↓            ↓
  验证权限   业务逻辑校验   执行 SQL
```

---

#### 4. 流程与逻辑
- 主流程图或时序图
- 关键分支（成功、失败、异常）
- 状态变化
- 接口/数据模型摘要

---

#### 5. 实现计划
- 拆分开发步骤
- 受影响文件/目录列表
- 注意事项（性能、安全、兼容性）

**示例**:
```
步骤：
1. 定义 BatchDeleteRequest DTO
2. 实现 Repository 层批量软删除方法
3. 实现 Use Case 层业务逻辑（权限、数量校验）
4. 添加 API Handler
5. 更新路由配置

受影响文件：
- src/adapters/http/users/dtos.rs
- src/adapters/persistence/postgres/user_repository.rs
- src/core/use_cases/users/batch_delete.rs
- src/framework/bootstrap/routes/users.rs
```

---

#### 6. 代码变更
- **已有文件**: 使用 diff 格式展示变更
- **新文件**: 贴完整代码块
- **复杂逻辑**: 写明功能注释（说明意图与使用场景）

**注释要求**:
```
✅ 好的注释（说明"为什么"）：
// 使用事务保证批量删除的原子性，避免部分成功部分失败
let mut tx = pool.begin().await?;

❌ 不好的注释（重复代码）：
// 开始事务
let mut tx = pool.begin().await?;
```

---

#### 7. 自检清单
在交付前，必须自检以下项目：

- [ ] **完整性**: 所有功能是否完整实现？
- [ ] **准确性**: 是否符合需求？有无理解偏差？
- [ ] **可测试性**: 能否编写单元测试？是否提供测试用例？
- [ ] **可复用性**: 代码是否可复用？有无过度耦合？
- [ ] **一致性**: 命名、风格、错误处理是否一致？
- [ ] **设计合理性**: 是否过度设计？是否违反 SOLID 原则？

## 📌 开发质量要求

### ✅ 必须遵守

1. **需求不清必须提问，不默认假设**
   - 遇到歧义或不确定的地方，立即提问
   - 不要根据"常识"或"经验"猜测需求

2. **方案可落地、命名统一**
   - 代码必须能实际运行，不写"示例代码"
   - 命名遵循项目规范（见 PROJECT.md）

3. **复杂逻辑和关键流程附带功能注释**
   - 说明意图和使用场景
   - 不要写显而易见的注释

4. **主动识别风险与边界**
   - 性能瓶颈（大数据量、并发）
   - 安全隐患（SQL 注入、XSS、权限）
   - 边界条件（空值、极大/极小值）

5. **避免炫技或过度设计**
   - 优先简单可维护的方案
   - 不引入不必要的抽象或模式

6. **新增能力必须可测试**
   - 提供测试策略或测试用例
   - 说明如何验证功能正确性

7. **新依赖需说明理由与风险**
   - 为什么需要这个库？
   - 有没有更轻量的替代方案？
   - 是否增加安全风险或维护负担？

---

## 🏗️ 设计与实现约束

### ✅ 必须遵守

1. **保持现有业务逻辑稳定**
   - 新增功能优先采用继承或组合
   - 避免修改核心业务逻辑

2. **必要修改旧代码时**
   - 提前说明修改原因和影响范围
   - 提供 diff 对比
   - 提供回滚方案
   - **获得确认后执行**

3. **未获"生成文档"指令前，不输出最终文档**
   - 讨论阶段可以发草案
   - 最终文档需要明确指令

4. **未获执行确认前，不提交成品代码**
   - 方案讨论阶段可以发伪代码或草案
   - 成品代码需要明确的"交付"指令

## 🧩 设计原则（SOLID + CRP）

### 1. SRP - 单一职责原则（Single Responsibility Principle）
**定义**: 一个类/模块应该只有一个引起它变化的原因

**示例**:
```
❌ 不好：
class UserService {
  createUser()
  deleteUser()
  sendEmail()        // ❌ 邮件发送不属于 User 职责
  generateReport()   // ❌ 报表生成不属于 User 职责
}

✅ 好：
class UserService {
  createUser()
  deleteUser()
}

class EmailService {
  sendEmail()
}

class ReportService {
  generateReport()
}
```

---

### 2. OCP - 开闭原则（Open/Closed Principle）
**定义**: 对扩展开放，对修改封闭

**示例**:
```
❌ 不好：每次添加新支付方式都要修改 process()
class PaymentProcessor {
  process(type) {
    if (type == "alipay") { ... }
    else if (type == "wechat") { ... }
    // 添加新支付方式需要修改这里 ❌
  }
}

✅ 好：通过接口扩展
trait PaymentMethod {
  fn process(&self);
}

class AlipayPayment implements PaymentMethod { ... }
class WechatPayment implements PaymentMethod { ... }
// 添加新支付方式只需实现接口 ✅
```

---

### 3. LSP - 里氏替换原则（Liskov Substitution Principle）
**定义**: 子类必须能够替换其父类

---

### 4. ISP - 接口隔离原则（Interface Segregation Principle）
**定义**: 不应该强迫客户端依赖它不使用的方法

---

### 5. DIP - 依赖倒置原则（Dependency Inversion Principle）
**定义**: 高层模块不应依赖低层模块，两者都应依赖抽象

---

### 6. CRP - 合成复用原则（Composite Reuse Principle）
**定义**: 优先使用组合而非继承

---

## 🚫 非目标（禁止行为）

### ❌ 禁止

1. **未确认上下文前，输出代码或文档**
   - 必须先确认理解需求

2. **做无关重构或擅自改变业务流程**
   - 只做要求的功能
   - 不做"顺便优化"

3. **省略测试、回滚方案或文档同步提示**
   - 交付必须完整

4. **讨论阶段输出最终版文档**
   - 讨论阶段只能发草案

5. **过度设计或炫技**
   - 保持简单可维护

## 📝 文档管理规范

### 文档分类

```
doc/
├── requirements/     # 功能需求文档
├── business/        # 核心业务逻辑文档
├── features/        # 功能实现指南
└── framework/       # 架构概要文档
```

### 文档命名规范

格式：`[功能/模块]_[类型]_[日期].md`

**示例**:
- `用户登录_需求_20260119.md`
- `订单处理_业务逻辑_20260119.md`
- `支付功能_实现指南_20260119.md`

---

### 文档更新策略

#### 🟢 直接更新现有文档（优先）
**适用场景**:
- 功能优化、bug 修复
- 添加新的业务规则
- 完善现有功能

**操作**:
- 直接修改当前日期的文档
- 在文档末尾添加"更新记录"章节

**示例**:
```markdown
# 更新记录
- 2026-01-19 14:30：添加密码强度验证
- 2026-01-19 16:20：优化错误提示逻辑
```

---

#### 🟡 创建新版本文档
**适用场景**:
- 重大功能重构
- 架构层面变更
- 技术栈升级

**操作**:
- 创建新日期版本（如：`登录功能_实现指南_20260120.md`）
- 旧版本移动到 `archive/` 目录

---

#### 🔴 需要用户确认
**适用场景**:
- 影响多个模块的变更
- 数据结构重大调整
- 向后不兼容的修改

---

### 文档同步提醒格式

在交付代码后，必须提醒用户更新文档：

```markdown
✅ 开发完成！

📝 建议更新文档：
1. 更新：`doc/features/登录功能_实现指南_20260119.md`
   - 在"更新记录"中添加密码验证功能

2. 无需更新：架构文档（无结构性变更）

3. 创建新文档：无（本次为功能优化）
```
